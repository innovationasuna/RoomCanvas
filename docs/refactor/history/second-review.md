# RoomCanvas 重构建议

> 本文保留重构前的审查意见，部分问题现已修复。最终实施与验证以[重构验收记录](../validation.md)为准。

原文中的 `refactor.md` 对应归档后的[最初代码审查](initial-review.md)。

2026-11-16

refactor.md 的判断可靠，可以照它做；我建议调整顺序，并补上它没有审的运行过程。

- **核对：** 对照代码查了 16 条，全部属实。
- **顺序：** 先单独修三处会让线上任务随机失败的问题；坐标错位和抽出碰撞服务合成一步；上传阻塞提到高优先级。
- **最大的遗漏：** 一次房间重建用了 9 次尝试、约 8 小时。流水线可靠性应该排在性能优化之前。
- **统一的验收标准：** 每件事只有一个来源。位姿、GPU 锁、任务进度、线上代码、配置现在都有两个以上。
- **开工前先做准备：** 部署只走 git，并在浏览器里测出一份耗时基线，否则后面无法确认改动生效。

## 核对结果

refactor.md 里我对照代码核对了 16 条，全部属实，其中 3 条需要补充说明。核对基于 `main` 的 `b0ccbeb`（#68 合并之后）。

| refactor.md 的说法 | 结论 | 说明 |
| --- | --- | --- |
| 碰撞索引在主线程和 Worker 各建一次，增删物品全屋重建 | 属实 | `rebuildCollision()` 先调 `buildCollision`，再把同一份几何发给 Worker 重建 |
| PBR 物体没有轻量模型 | 属实 | 烘焙成功后直接返回；前端缺 preview 时克隆完整模型当轻量模型 |
| 漫游一次身体检测做 9 次全场景射线 | 属实，实际更重 | `free()` 一次是 1 + 8×9 = 73 条射线，每条都扫整个渲染场景，没有加速结构 |
| 房间解压持有全局锁 | 属实，影响更大 | 健康检查、任务列表、回放读取都要先拿这把锁，见下一节 |
| 回放 `drop()` 不清理 `wallFades` | 属实 | 旧模型的墙面材质每帧仍被遍历 |
| 移动家具后导入或删除，碰撞和支撑错位 | 代码路径属实 | 几何提取用 `matrixWorld`，已含家具位移；复现我没有重跑 |
| 原始重叠变成永久豁免 | 属实，但是有意设计 | 代码注释写明扫描时相交的两件物体永不互相阻挡，见下一节 |
| 并发保存共用临时文件 | 属实 | `items.tmp` 和 `answer.json.part` 都是写死的文件名 |
| 两条重建服务没有共用 GPU 锁 | 属实，已在服务器确认 | student2-8 没有设置 `VIEWFORGE_GPU_LOCK`，两边各用各的锁文件 |
| 物体未完成就可标定，标定随后失效 | 属实 | 标定键包含 COVER 的坐标变换，变换一写入键就变 |
| `compile_room()` 忽略烘焙返回码 | 属实 | `bake_room` 的结果没有被检查 |
| TRELLIS 服务分支丢掉强制重建 | 属实 | 命令里硬编码 `--skip-existing` |
| 可开合部件缓存不绑定来源房间 | 属实 | 只比较 `plan.json`，不看 `Room.blend` 有没有变 |
| 大网格 `Math.min(...array)` 报错 | 属实 | `placement.mjs` 第 91、96 行 |
| 房间服务 503 时代理不回退缓存 | 属实 | `room_answer` 遇到 HTTP 错误直接透传，只有连不上才用缓存 |
| 两份手势 tracker 重复、`scene-editor.js` 过大 | 属实 | 见「refactor.md 没覆盖的重构方向」一节的数字 |

没有核对的有三处：各项性能计时、DA3 的 float64 和双份 pointmap、物体上传的同步复制。

## 对 refactor.md 的修改建议

共 11 条：4 条调整优先级和顺序，5 条给出更小的修法，2 条是文档本身要补的内容。

### 优先级和顺序

1. **第一批先单独修三处会让线上任务随机失败的问题。** GPU 锁、并发保存、`compile_room` 的成功判断，这三处改动小、互不依赖，可以先出一个 PR。坐标错位和碰撞规则改动更大，放在其后。
2. **坐标错位的修复就是拆分的第一步，不要等到第三批。** 修它需要「稳定的局部几何，位姿只应用一次」，这正是把碰撞服务从 `scene-editor.js` 里抽出来时要定的接口。建议两件事合成一个 PR：抽出碰撞服务，同时修掉错位。增量索引之后在这个接口上做。
3. **「上传解压阻塞」从中提到高。** 房间服务的健康检查、任务列表、回放读取都要先拿到 `jobs.lock`，而本地代理在有缓存时只等 8 秒。上传一个大的扫描包时，网页会以为服务断了或退回旧缓存，用户看到的是「一上传页面就挂」。
4. **第二批性能优化，先在浏览器里测，再动手。** 文档自己也说明 Node 里的 CPU 计时不能换算成浏览器帧率。先测一次真实浏览器里的加载和漫游耗时，确认用户能感觉到卡，再决定做不做增量索引和碰撞代理。

### 更小的修法

5. **原始重叠：先定规则，再改代码。** 现在的豁免是有意的，为的是扫描时就挨着的家具能搬得动。建议按穿透深度判断：不超过初始值就放行，超过就阻挡。这样原来能搬的还能搬，又不会让两件物体完全重合。
6. **原子写入不用新造工具。** `object-reconstruction/scripts/dimensions.py` 的 `atomic_json` 已经是正确写法：同目录随机文件名，再替换。`room_cache.save` 改用同样的写法；`small_objects` 的问题是多线程共用 `self.items`，给 `save()` 加一把锁就能解决「旧状态覆盖新状态」。
7. **漫游直接复用碰撞系统已经建好的三角形树。** 不必再建一套空间索引。同一份几何两边共用，漫游和摆放对「哪里有障碍」的判断也不会再出现分歧。
8. **PBR 物体的碰撞代理不用重做整套 LOD。** 当初跳过 preview，是因为旧生成器会把贴图转回顶点色。碰撞代理本来就不需要材质，照常生成一个减面、去掉材质的网格就够了。
9. **两处缓存各改一行左右。** 可开合部件：把来源 `Room.blend` 的大小和修改时间（或哈希）写进 `plan.json` 一起比对。TRELLIS：把强制重建参数传下去，强制时不加 `--skip-existing`。

### 文档本身

10. **开头写明基于哪个提交。** 文中所有行号都对应某个版本，后续 PR 一合并就会偏。从测试数字看应该是 `b0ccbeb`。
11. **手势 tracker 的重复排到最后。** 两个文件分别只有 36 行和 44 行，相差 14 行，合并的收益很小。

## refactor.md 没覆盖的重构方向

refactor.md 审的是代码，没有审运行过程。从这几天在服务器上部署和跑房间的经验看，还有五个方向值得纳入。

### 同一件事有两个以上的来源

这是项目里最常见的问题根源，refactor.md 找到的坐标错位、GPU 锁、缓存失效都属于这一类。重构时建议把「每件事只有一个来源」当作统一的验收标准。

| 事实 | 现在的来源 | 建议的唯一来源 |
| --- | --- | --- |
| 家具位姿 | 渲染对象的 `matrixWorld` 和 layout 各一份 | 场景模型里的局部几何加位姿，渲染、碰撞、保存、撤销都读它 |
| 障碍几何 | 摆放用碰撞三角形树，漫游用渲染场景的射线 | 同一份碰撞几何 |
| GPU 占用 | 房间用 `runtime/locks/gpu-<UUID>.lock`，物体用 `cache/gpu.lock` | 按 GPU UUID 的一把锁 |
| 任务进度 | `job.json`、`pipeline.log`、`exit` 文件、`trace.jsonl`、文件修改时间 | `trace.jsonl` 一份带版本号的事件记录，回放只读它 |
| 线上代码 | git 提交，加上用 scp 覆盖的文件 | 只有 git 提交，服务能报告自己的提交号 |
| 运行配置 | 4 个 env 文件，约 100 个变量，5 种前缀 | 一个入口文件和一张变量表 |

后三行的具体情况：

- **任务进度。** 回放脚本 `room_replay.py` 有 910 行，其中相当一部分是在记录缺失时按文件时间和日志去推断。最近两个回放故障都出在这里：失败重试留下的记录被当成最后一步的开始；Agent 直接调 Blender 编译时不写 `room_built`，部件出现的时刻只能靠猜。建议给事件记录定一个版本化的格式，所有编译入口都写，旧任务一次性转换，然后删掉推断代码。
- **线上代码。** 服务器曾经有 16 个文件是 scp 上去但没有提交的，所在分支也落后 `main` 两个 PR，其中至少 3 个文件和后来合并的版本不一致。`start_server.sh` 只有启动和查看状态，更新代码要手工找进程杀掉。建议加 `stop` 和 `restart`，健康检查返回提交号，部署只走 `git pull`。
- **运行配置。** 配置分在 `runtime/server-env.sh`、`object-reconstruction/configs/local.env`、`room-reconstruction/.env` 和 `models.env`。变量前缀有 `LR_`（79 个）、`LITEREALITY_`（14 个）、`ROOMCANVAS_`、`VIEWFORGE_` 等。GPU 锁的缺口就是两边各读各的配置造成的。

### 一次房间重建的失败和耗时

Room_3934 在 2026-11-12 从 14:14 跑到约 22:10，共 9 次尝试，最后成功那次光 author 阶段就用了 8737 秒。这比 refactor.md 里任何一项性能问题对用户的影响都大。期间有人工修问题后再重试。

| 尝试 | 结果 |
| --- | --- |
| 第 1、2 次 | 物体重建不完整（`Wall4_Door_1`），各跑了 20 到 30 分钟后失败 |
| 第 3、4 次 | 选视角时找不到文件，和扫描包的目录结构有关 |
| 第 5、7 次 | author 会话到 3600 秒上限，整段失败 |
| 第 6、8 次 | 没有留下可读的结束原因 |
| 第 9 次 | 成功 |

建议四件事：

1. **上传时就检查输入。** 目录结构、必需文件在几秒内报错，而不是跑 30 分钟以后。
2. **每次失败写一条结构化原因。** 包括阶段、类别、是否值得重试。只有瞬时故障才自动重试，输入问题和程序错误直接报给用户。
3. **author 阶段能从中途接着跑。** 它是最长的单个阶段，超时后已经能保留房间，下一步是让新会话从保留的房间和已完成的步骤继续。
4. **把各阶段耗时和失败类别汇成一张表。** 用它决定先优化哪里。refactor.md 对 Cycles 渲染的猜测也用这张表来验证。

### 「完成」没有统一的含义

Room_3934 的 publish 阶段报告了质量检查违规，任务状态仍是「完成」。这个房间最终有 0 个可开合部件和一件悬空的储物柜，网页上看不出来。refactor.md 第 6 条里 `compile_room` 忽略返回码是同一类问题。

建议每个阶段返回同一种结果：状态、警告列表、产物路径。任务状态由它们汇总得出，网页显示「完成，有 N 项待处理」。

### 测试和测量的缺口

- **CI 漏跑。** `web/scripts/` 下 3 个 Node 测试文件、11 个检查脚本里的 6 个、整个 `android-app` 都不在 CI 里。
- **回放的画面逻辑没有测试。** `room-view.mjs`（672 行）和 `materialize.mjs`（268 行）没有任何自动化测试。机位选择、成形顺序、何时该停留都是纯计算，可以抽成函数来测。
- **没有浏览器内的耗时测量。** 自动化浏览器的后台窗口会被降到约每秒 1 帧，测不了流畅度。建议页面加一个 `?perf=1` 开关，记录加载各步耗时和帧间隔。第二批「先测再改」靠的就是它。

### 旧代码、重复实现和大文件

- **归档代码还在主干。** `object-reconstruction/legacy/` 有 46 个文件，其中两个 JS 各约 1.2 万行，服务不加载。
- **漫游有三套实现。** `web/editor/walk.mjs`、`room_ops/walk/app.js`（1046 行，从别的仓库复制来，注释要求不要改）、Android。
- **大文件直接进了 git。** 当前文件树约 345 MB，其中物体示例数据约 152 MB，两个样例房间模型约 101 MB。
- **服务层。** 有 4 个手写的 `http.server` 服务，物体服务另用 starlette。不建议为统一而换框架。只需要在房间服务里把任务状态、执行、HTTP 三件事分开，让锁只保护状态更新，解压阻塞也随之解决。
- **名字有四套。** `litereality` 出现在 249 个文件，`viewforge` 46 个，`hausen3d` 11 个，`RoomCanvas` 43 个。不建议改包名，改动面大而用户看不到；只统一对外的环境变量前缀，旧名继续兼容。

## 建议的实施顺序

分六批，每批一到几个 PR，每个 PR 只做一件事。和 refactor.md 的三批相比，多了最前面的准备和中间的流水线可靠性，性能往后挪了一位。

| 批次 | 范围 | 验收 |
| --- | --- | --- |
| 0 准备 | 部署只走 git，`start_server.sh` 加 `stop` 和 `restart`，健康检查返回提交号；页面加 `?perf=1`；CI 补跑漏掉的测试 | 服务器工作区干净；有一份真实浏览器里加载和漫游耗时的基线 |
| 1 线上稳定 | GPU 锁、并发保存、`compile_room` 返回码、解压移出全局锁、503 回退缓存、`Math.min` 边界 | 并发保存和「上传时读进度」有测试；房间和物体任务同时排队时不会同时进推理 |
| 2 编辑器正确性 | 抽出碰撞服务并修坐标错位；原始重叠改按穿透深度；物体处理完才能标定 | 「移动后导入或删除」「重叠后分开再穿过」「处理中标定」三组测试通过 |
| 3 流水线可靠性 | 上传时检查输入；结构化失败原因；统一阶段结果和「完成」的含义；可开合部件和 TRELLIS 的缓存绑定输入；事件记录定版本 | 同一个扫描包重跑，尝试次数和总耗时低于 Room_3934 的 9 次、约 8 小时；回放不再读文件时间 |
| 4 性能 | 按基线决定做哪几项：碰撞代理、增量索引、漫游复用碰撞几何、DA3 改 float32、回放模型释放 | 每项和基线对比有可见改善才合并 |
| 5 清理 | 归档代码、大文件、手势 tracker、`scene-editor.js` 余下的拆分 | 测试数量不减，行为不变 |

准备批要最先做。没有它，后面每一批都无法确认改动是否真的上了线、是否真的变快。

## 待决定事项

下面六项需要项目负责人拍板，每项都给了我的建议。

1. **原始重叠的规则。** 是否采用「穿透深度不超过初始值就放行」。建议采用。
2. **流水线可靠性和性能谁先。** 建议可靠性在前，因为一次重建约 8 小时比帧率对用户影响大。如果近期要演示编辑器，可以对调。
3. **`object-reconstruction/legacy/` 是否移出主干。** 建议移出，git 历史里仍然能找回。
4. **大文件是否迁到 Git LFS 或发布附件。** 建议迁，但会改变克隆和 CI 取样例的方式，可以放到最后。
5. **是否统一环境变量前缀。** 建议统一对外的那部分，旧名继续兼容；包名不动。
6. **回放的待提交改动。** 本地还有回放特效和运镜的改动没有提交。建议先合并它，再做「回放模型释放」那一项，因为成形动画新增的材质缓存也要一起释放。
