# 阶段 3 · 性能测试

> 依据《光影渲染性能优化方案2（当前新方案）》第 6 章执行。
> 目标：在 RTX 4050 上以手机横屏分辨率 2640×1200 复现场景，测量 PC-01 ～ PC-04 的平均 FPS、p50/p95/p99 帧时间、GPU/CPU 帧时间、显存占用与长时间稳定性，验证 60 FPS 目标。
> 日期：2026-11-08。

---

## 0. 结论

1. **8 个配置（PC-01 ～ PC-04 × PCSS/DPCF/PCF）在 2640×1200 下全部达到 60 FPS**：平均 59.5 ～ 60.0 FPS，其中 7 个 ≥ 59.99 FPS。
2. **渲染耗时远低于 16.67 ms 预算**：最重的 PC-04 + PCSS 在 40 s 测试中 GPU p95 = **11.88 ms**、CPU p95 = 1.84 ms；10 分钟长稳中 GPU p95 = **14.55 ms**，仍留约 13% 余量。
3. **PCSS 是三者中最贵的阴影类型**：同场景下比 DPCF 多 **+3.3 ～ 3.8 ms** GPU 时间（约 +53%）；DPCF 与 PCF 基本持平。
4. **后处理（SSAO + Filmic + FXAA）成本很低**：PC-03 → PC-04 仅增加约 0.1 ～ 1.2 ms GPU 时间（平均约 0.7 ms，差异在跨运行 DVFS 噪声范围内）。
5. **显存占用可控**：PC-01/02 约 561.7 MB，PC-03（阴影）584.7 MB，PC-04（全部后处理）613.2 MB。10 分钟长稳中显存无增长（613.1 → 612.6 MB）。
6. **10 分钟长稳无性能衰减**：逐分钟 59.93 ～ 60.01 FPS，GPU 温度稳定在 57 ～ 58 °C，功耗约 23 ～ 27 W。
7. **方法学上发现并修复了三个会严重污染数据的陷阱**（详见 §2.4）：帧跳过循环导致后端命令队列积压、Windows 对后台进程的电源节流（单次等待可达 740 ms）、1 Hz WMI 显存采样本身造成每秒一次的 29 ms 节流尖峰。修复前 PC-01 只能测到 15.9 ～ 40 FPS，修复后稳定 60.0 FPS。

## 2. 测试方法

### 2.1 测试组与预设

四组测试对应方案 §6.1，模型、相机位姿、分辨率、曝光全部保持一致，只逐级打开渲染模块：

| 测试编号 | 预设 | 场景配置 |
|---|---|---|
| PC-01 | `p1` | 仅模型 + 基础材质 + IBL（无灯光、无阴影、无后处理） |
| PC-02 | `p2` | + 完整灯光（日光 + 顶灯 + 窗灯），无阴影 |
| PC-03 | `p3` | + 全部实时阴影（4 级 1024 日光级联 + 512 窗灯聚光阴影） |
| PC-04 | `p4` | + 全部后处理（SSAO、Filmic 色调映射、FXAA） |

PC-03 / PC-04 各跑 `pcss`、`dpcf`、`pcf` 三种阴影类型，共 8 个用例。

### 2.2 采集指标

- **平均 FPS**：测量窗口内渲染帧数 / 墙钟时间。
- **帧间隔 p50/p95/p99**：相邻渲染帧 `beginFrame` 时间戳之差。
- **CPU 帧时间**：主线程 `renderer->render()` + `endFrame()` 的耗时。
- **GPU 帧时间**：`FrameInfo::gpuFrameDuration`（GPU 时间戳查询），p50/p95/p99。
- **显存**：Windows 性能计数器 `GPUProcessMemory.LocalUsage`（GPU 本地显存），按 PID 汇总。
- **温度/频率/功耗**：`nvidia-smi` 每 15 s 采样。

> 注：`FrameInfo::gpuFrameComplete` 在当前 Vulkan 后端始终为 -1，不作为指标使用。

### 2.3 计时纪律

| 措施 | 取值 | 原因 |
|---|---|---|
| 矩阵前预热 | 20 s（PC-04 无节流） | 统一 GPU 频率/功耗状态，避免第一个用例被冷启动惩罚 |
| 每组预热 | `--warmup=5` | 排除管线编译与缓存预热帧 |
| 每组时长 | `--duration=40`（有效窗口约 35 s，≈ 2100 帧） | 覆盖稳定状态 |
| 帧率节流 | `--max-fps=60`（sleep 到截止前 2 ms，再自旋补齐） | 模拟 60 Hz 垂直同步；纯 `SDL_Delay` 精度不足 |
| 进程优先级 | `High` | 还原前台应用环境，避免 Windows 电源节流（见 §2.4） |
| 显存采样 | 与计时矩阵分离 | 1 Hz WMI 查询本身会污染节流（见 §2.4） |

### 2.4 三个方法学陷阱（重要）

**（1）帧跳过循环导致后端命令队列积压。**
`Renderer::beginFrame()` 在 GPU 仍忙时会返回 `false`，建议调用方跳过该帧。若调用方立刻重试（紧凑循环），每次调用都会向驱动线程排入一个 `tick()` 并 flush，命令队列被灌满，反而延迟了帧跳过器自己等待的 fence，形成活锁——表现为 100 ～ 300 ms 的周期性卡顿。修复：跳过时 `SDL_Delay(1)`，模拟真实应用回到事件循环。

**（2）Windows 对后台进程的电源节流。**
由自动化脚本启动的进程属于后台进程，Windows 会把其定时器唤醒合并、延迟数百毫秒。实测 `pace_max`（一次节流等待的耗时）最高 **739.8 ms**，PC-01 因此只测到 15.9 FPS。将进程优先级提升到 `High` 后，同一场景立刻变为 **60.00 FPS，帧间隔 p50/p95/p99 = 16.667 / 16.672 / 16.681 ms**。这是测量环境问题，不是渲染问题。

**（3）WMI 显存采样干扰节流。**
`Get-CimInstance GPUProcessMemory` 单次查询约消耗 15 ms，按 1 Hz 采样时，每一秒恰好出现一次 `pace_max ≈ 29 ms` 的尖峰。显存是静态指标，因此计时矩阵中关闭采样，显存在单独的采样轮次中获取。

## 3. 60 Hz 验收结果（PC-01 ～ PC-04）

有效窗口约 35 s / 2098 帧，进程优先级 High，显存采样关闭。

| 用例 | 平均 FPS | 跳过帧 | 帧间隔 p50 | p95 | p99 | CPU p50 | p95 | p99 | GPU p50 | p95 | p99 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| PC-01 `p1` | 60.01 | 0 | 16.67 | 16.70 | 27.33 | 0.26 | 0.62 | 0.94 | 6.30 | 6.32 | 6.33 |
| PC-02 `p2` | 59.99 | 0 | 16.67 | 16.67 | 29.20 | 0.42 | 0.94 | 1.32 | 4.74 | 7.55 | 7.66 |
| PC-03 PCSS | 60.00 | 2 | 15.99 | 28.22 | 29.51 | 0.83 | 2.54 | 2.93 | 9.57 | 9.83 | 9.94 |
| PC-03 DPCF | 60.00 | 1 | 15.74 | 28.69 | 29.61 | 0.80 | 2.56 | 2.93 | 6.25 | 6.53 | 6.56 |
| PC-03 PCF | 60.00 | 1 | 15.74 | 28.79 | 29.77 | 0.69 | 1.36 | 2.40 | 6.31 | 6.45 | 6.46 |
| PC-04 PCSS | 59.99 | 2 | 15.74 | 28.69 | 29.59 | 0.75 | 1.84 | 2.72 | 10.80 | 11.88 | 12.08 |
| PC-04 DPCF | 59.51* | 2 | 16.67 | 16.68 | 16.78 | 0.66 | 0.99 | 1.92 | 7.00 | 7.26 | 7.33 |
| PC-04 PCF | 59.99 | 1 | 16.66 | 17.00 | 29.08 | 0.74 | 2.53 | 3.06 | 6.44 | 6.50 | 6.51 |

单位：ms。* PC-04 DPCF 的 59.51 FPS 来自一次孤立的 286 ms 系统级停顿（>50 ms 的帧仅 1 帧），其余帧间隔 p99 仅 16.78 ms。

### 3.1 帧间隔抖动说明

所有用例中超过 20 ms 的帧均为“错过一个 15.6 ms 系统 tick”的单帧滑档（间隔约 30 ms），**没有出现 > 50 ms 的渲染卡顿**（唯一例外即上表的 286 ms 系统停顿）。滑档比例为 0.1% ～ 10.2%，且与 GPU 耗时无相关性，属于 headless 环境下 `SDL_Delay` 节流的调度抖动，而非渲染性能问题。

因此本阶段以 **GPU / CPU 帧时间**作为“帧时间是否满足预算”的判据：最重的 PC-04 PCSS 的 GPU p95 = 11.88 ms，低于 16.67 ms 预算约 29%；CPU p95 仅 1.84 ms。

### 3.2 逐组分析

- **PC-01 → PC-02（加灯光）**：GPU p50 从 6.30 ms 变为 4.74 ms。数值不升反降，原因是笔记本 GPU 的动态调频（DVFS）——轻负载时 GPU 会降频，跨运行比较存在 ±20% 以上的噪声。可参考的是无节流模式：p1 = 2.94 ms、p2 = 2.98 ms，说明三个灯光的逐像素开销在当地分辨率下很小。
- **PC-02 → PC-03（加阴影）**：DPCF/PCF 下 GPU p50 约 +1.5 ms，PCSS 下约 +4.8 ms。阴影是四组中开销最大的一级。
- **PC-03 → PC-04（加后处理）**：同阴影类型下 GPU p50 增加约 0.1 ～ 1.2 ms（平均约 0.7 ms；PCF 组仅 +0.13 ms，差异在跨运行 DVFS 噪声范围内），SSAO + Filmic + FXAA 合计不到一帧预算的 8%。

## 4. PCSS / DPCF / PCF 对比

| 用例 | GPU p50 (ms) | GPU p95 (ms) | 相对 DPCF（p50） |
|---|---|---|---|
| PC-03 PCSS | 9.57 | 9.83 | +3.32 ms（+53%） |
| PC-03 DPCF | 6.25 | 6.53 | 基线 |
| PC-03 PCF | 6.31 | 6.45 | +0.06 ms（+1%） |
| PC-04 PCSS | 10.80 | 11.88 | +3.80 ms（+54%） |
| PC-04 DPCF | 7.00 | 7.26 | 基线 |
| PC-04 PCF | 6.44 | 6.50 | −0.56 ms（−8%） |

结论：

1. **PCSS 比 DPCF 贵约 50%**，与直觉一致（PCSS 需要 blocker search + 变半径 PCF）。
2. **DPCF 与 PCF 基本同价**，差异在跨运行 DVFS 噪声范围内。
3. 结合阶段 2 的视觉结论（桌面 Vulkan 上 PCSS 有亮色点状漏光，DPCF 干净），**DPCF 是当前更优选择**：既没有 PCSS 的视觉缺陷，又便宜约 3.3 ～ 3.8 ms。

## 8. 与 Android 端的对照和启示

方案记录的手机端基准：平均约 56 FPS、p95 帧时间约 16.56 ms、p99 约 83.22 ms。

| 维度 | Android 基准 | RTX 4050 桌面 |
|---|---|---|
| 分辨率 | 2640×1200 | 2640×1200 |
| 平均 FPS | ~56 | 59.98（PC-04 PCSS，10 min） |
| p95 帧时间 | 16.56 ms | GPU 14.55 ms / CPU 2.86 ms |
| p99 帧时间 | 83.22 ms | GPU 14.73 ms（墙钟 29.62 ms 为节流抖动） |

结论与启示：

1. **分辨率不是桌面端的瓶颈**：在相同 2640×1200 下，RTX 4050 的 PC-04 PCSS 仍有约 13% 的 GPU 余量。
2. **阴影类型是最值得优化的开关**：PCSS → DPCF 在桌面端省下约 3.3 ～ 3.8 ms/帧（约 50% 阴影开销）。手机端若同样以 PCSS 为基线，切到 DPCF 可能显著改善 p95/p99。
3. **后处理不是主要矛盾**：SSAO + Filmic + FXAA 合计约 0.1 ～ 1.2 ms（平均约 0.7 ms），优先级低于阴影。
4. **显存压力不来自本场景**：2640×1200 下完整场景仅 613 MB；手机端的显存/带宽压力更可能来自 AR 相机纹理、UI 合成与更高分辨率的中间缓冲。
5. 桌面端 Vulkan 与手机端 GPU/驱动不同，上述毫秒数不能直接换算到手机；可比的是**各项开销的相对比例**（阴影 ≫ 后处理 > 灯光）。

## 9. 已知限制

1. **无垂直同步**：headless swapchain 的 present 是空操作，`--max-fps=60` 只是模拟 vsync。真实 Android 应用由 SurfaceFlinger/Choreographer 驱动，帧间隔由系统合成器决定。
2. **GPU 动态调频**：笔记本 4050 在轻负载时会降频到 690 ～ 780 MHz，重负载稳定在约 1350 ～ 1500 MHz。因此跨运行比较 GPU 毫秒数有 ±20% 以上噪声，同一次运行内的 p50/p95 才是可靠值。表中 PC-01/PC-02 的 GPU 时间即受此影响。
3. **帧间隔 p95 中的 29 ～ 30 ms 滑档**是 Windows 定时器/调度抖动，不属于渲染耗时；GPU/CPU 帧时间不受影响。
4. **PCSS 视觉缺陷**：桌面 Vulkan 上 PCSS 有亮色点状漏光（阶段 2 §5.2），计时仍有效，但视觉验收应以 DPCF 为准。
5. **Filament 版本**：桌面端 1.68.2 与 SceneView 2.3.4 一致，但 Android 端使用不同的着色器特化/驱动路径，绝对数值仅供比例参考。
6. 未使用 ETW / PresentMon（本机无管理员权限），帧数据全部来自应用内 `FrameInfo` 与逐帧 CSV。
